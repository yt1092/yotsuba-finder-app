# YOTSUBA FINDER

## 概要

カメラや写真から、四つ葉のクローバーを見つける PWA（ブラウザで動くアプリ）です。
検出は、すべて端末の中（ブラウザの中）で行います。写真は端末の外に出ず、外部の API やサーバーには通信しません。
見つけた候補は、使う人が目で確かめて「図鑑に入れる」かを選びます。まちがいを「入れない」と教えると、その端末の中で、候補を出すしきい値が少しだけ合っていきます（端末の中のしきい値の調整だけです。教えた内容を学習データに戻して、モデルを学習し直す機能は、まだありません）。

## 特徴

- カメラでリアルタイムに探す（金色の枠 = 四つ葉の候補、細い白の枠 = 三つ葉）。候補が安定したら止まり、確認のポップアップを出す
- 写真から探す（全体と 2×2 のタイルで探し、三つ葉の本数も数える）
- 確認のポップアップで、使う人が「図鑑に入れる」「入れない」を選ぶ。たしかさのめやすは 3 段階の記号（●●● / ●●○ / ●○○）だけで、数字やパーセントは出さない
- 図鑑・日記カード（ひとこと・手書き・シール）・きろく（レベル・バッジ）
- 今日のよつば: 1 日に 1 回、この端末の中の小さなモデル（DiT・flow matching。数式で作った形だけで学習）が、四つ葉の形を作る。本物の四つ葉の写真から直接は学習していない（写真は、数式の形の範囲を決める測定にだけ使った）。形は、日付と端末ごとの値から決まり、端末どうしは通信しない。モデルが使えないときは、あらかじめ数式で作った 60 個から 1 つを出し、図鑑には「あらかじめ作った形」と書く（下の「今日のよつば」）
- 「入れない」は、まちがいの記録として端末の中にだけ残り、候補を出すしきい値を少しだけ合わせる（設定でオン・オフ）。端末の中のしきい値の調整だけで、学習データに戻す機能は、まだない
- 外部通信なし・オフラインで動く（Service Worker のキャッシュ）。テスト `npm run test:e2e` で確かめている
- データは、この端末の中だけにあり、設定の「すべてのデータを消す」で、いつでも消せる（下の「プライバシー」）
- 設定の「書き出しと 読み込み」で、図鑑・日記・きろく・まちがいの記録・設定を 1 つの JSON ファイルにして保存し、あとで戻せる（下の「データを守る」）

## 技術

- Vite + TypeScript（素の DOM）。画面ごとの HTML
- 検出: 自作の YOLO（Ultralytics YOLO11n をもとに学習）を ONNX にして、onnxruntime-web で動かす（Web Worker の中）。モデル・wasm・フォントは、すべて自分のサイトから配る
  - カメラは WASM（1 スレッド）。iPhone の診断で、カメラで WebGPU を使うと、時間がたつと（約 10 秒）Safari が落ちたため、カメラでは WebGPU を使わない（下の「カメラの検出は WASM」）
  - 写真から探すは WebGPU、だめなら WASM
- 保存: IndexedDB（図鑑・まちがいの記録・きろく・調整の記録）
- 学習と評価: `training/`（学習は Colab。評価のスクリプトは、写真ごとに途中保存して、続きから再開できる）

### プライバシー（データは、この端末の中だけ）

- 写真・図鑑・ひとこと・日記の手書き・きろく（経験値・バッジ）・まちがいの記録・端末内の調整の記録・今日のよつばの形と端末ごとの値は、すべて、この端末のブラウザの中（IndexedDB など）にだけ保存する。外部のサーバーには送らない（外部通信なし。`npm run test:e2e` で確かめている）
- まちがいの記録を外に出すのは、設定の「書き出す」を、使う人が押したときだけ（zip を共有・ダウンロード）
- 設定の「すべてのデータを消す」（`src/lib/wipe.ts`）で、いつでも消せる。2 回押すと消える（まちがって押さないように）
  - 消えるもの: 図鑑（ひとこと・日記の手書きも記録の中にある）・最後に調べた写真・まちがいの記録・きろく（経験値・バッジ）・端末内の調整の記録・今日のよつばの今日の形と端末ごとの値
  - 消えないもの: チュートリアルの「見た」という印（設定から、もういちど見られる）・保存のしかたや今日のよつばの見た目などの設定・アプリとモデルのキャッシュ（検出のモデル・今日のよつばのモデル・wasm。オフラインで動くため）・カメラの許可（ブラウザの設定）
  - テスト `npm run test:e2e` の最後で、消えるものと残るものを確かめている

### オフライン対応のしくみ

サービスワーカーのひな形は `sw/sw.js` です。`npm run build` のときに `vite.config.ts` が、キャッシュするファイルの一覧とビルド ID を書き込み、`dist/sw.js` を作ります。

| キャッシュ | 対象 | 方針 |
|---|---|---|
| `yotsuba-finder-app-v<版>-<ビルドID>` | HTML | ネットワーク優先（つながらなければキャッシュ） |
| 同上 | `/assets/`（ハッシュ付きの JS・CSS・フォント） | キャッシュ優先 |
| `yotsuba-finder-models-v3` | `/models/`・`/ort/` | キャッシュ優先。新しい版を入れたら古い版を消す |

ビルドの中身が変わると画面用キャッシュの名前が変わり、古いものは自動で消えます。モデル用キャッシュはアプリを更新しても残るので、モデルを毎回ダウンロードし直すことはありません。

### 確認してから図鑑に入れる（既定。設定で「自動で入れる」に戻せる）

四つ葉を検出したら、画面の真ん中に確認のポップアップを出し、使う人が目で見て、図鑑に入れるか入れないかを選びます（`src/components/four-confirm.ts`。決める動きは `src/lib/four-review.ts`・テストあり）。

- 候補を 1 つずつ、まわりの景色つき・枠つきで拡大して見せる。「1/13」の順番・左右になぞる・「まえへ」「つぎへ」で移れる。「図鑑に入れる」「入れない」を押すと、次の候補に進む。候補が 10 個以上なら、最初に「ぜんぶ入れない」も出す
- 「ぜんぶ入れない」は、候補の写真の上（「1/12」の近く）に、枠線だけの控えめなボタンで置く（「図鑑に入れる」「入れない」とは離す）。押すと、まだ決めていない候補を全部「入れない」にする
- 全部決めたら（または × で閉じたら）、ポップアップを閉じる。決めた結果は、後ろの結果の画面だけに出す（以前は、ポップアップにも、まとめの文と「図鑑で見る」「別の写真を調べる」を出していて、結果の画面と同じ文・同じボタンが重なっていた。結果の画面は、読み込み直しても残り、日記カードや「四つ葉を見逃している」も使えるので、こちらに 1 つにした）
- 結果の画面の文（`src/lib/result-text.ts`・テストあり）

| 結果の状態 | 見出し | その下 |
|---|---|---|
| 四つ葉が見つからなかった | 四つ葉は 見つかりませんでした | 三つ葉が ◯本 ありました |
| 見つかったが、すべて「入れない」 | 四つ葉は ありませんでした | 三つ葉が ◯本 ありました |
| 一部だけ入れた・すべて入れた・自動で入れる | 四つ葉を ◯本 図鑑に入れました | 三つ葉が ◯本 ありました |
| × で閉じて、1 つも入れていない | 四つ葉は 図鑑に入れませんでした | 三つ葉が ◯本 ありました |
| 同じ写真の 2 回目 | この写真は、調べたことがあります | 経験値は、増えません（その下に、上のどれか） |
| ポップアップで、まだ決めていない（後ろの画面） | 四つ葉の候補を たしかめています | 三つ葉が ◯本 ありました |
| カメラ（図鑑に入れたとき） | 四つ葉を発見！ | 図鑑に入れました（「自動で入れる」なら、図鑑に自動で入れました） |

  三つ葉が 0 本のときは、その下の文を出さない
- 保存: 入れた候補が 1 つ以上のときだけ、その写真の記録を作り、入れた枠だけを四つ葉の枠として保存する（入れなかった枠は記録に残さない）。保存と四つ葉の経験値は `src/lib/save-four.ts`
- 「入れない」（「ぜんぶ入れない」も）は、まちがいの記録に「これは四つ葉じゃない」として自動で足す（端末の中だけ。同じ枠は重ねない）
- カメラ: 検出が安定したらスキャンを止め、そのフレームを同じポップアップで確認する。「図鑑に入れる」なら保存して、今までと同じカードを出す。「入れない」なら保存せずに、スキャンを再開する（その葉が一度視界から外れるまでは、また出さない）
- 設定の「保存のしかた」: 「確認してから入れる（おすすめ）」／「自動で入れる」（この端末のブラウザに残す）

**たしかさのめやす（3 段階。数字は出さない）**: 境目（`CONFIDENCE_LEVELS`）は、`training/calibrate.py` で、「その段階の枠のうち、本物が ○% 以上」と、95% の下限つきで言えるように決めています。

### 検出の枠の見た目（`src/lib/box-style.ts`・`src/components/scan-overlay.ts`・`src/components/leaf-photo.ts`）

- 四つ葉: 金色（#F5C242）の太い枠に、濃い縁取り（暗い写真でも明るい写真でも見える）・四隅の印・「四つ葉 ●●●」の小さなラベル（白いチップ・14〜15px）
- 三つ葉: 細い白の枠。ラベルは出さない（密集した場面で、うるさくならないように）
- 色だけに頼らない: 線の太さ・点線・四隅の印・ラベルでも区別できる
- カメラ: いちばんスコアの高い四つ葉を追い、安定するまで（直近 5 回のうち 3 回、ほぼ同じ場所）は金色の点線と、ラベルの右の進み具合の輪。安定してスキャンを止めたら実線にして、確認のポップアップを出す
- カメラの上に凡例（「四つ葉の こうほ」「三つ葉」）。初めて見たあとは、小さく（14px・うすく）。押せるものではない
- 写真の結果の画面・全画面で見るときも、同じ見た目（三つ葉の枠は押せない。四つ葉の枠は、押せる範囲 52px 以上）
- 四つ葉のラベルは、スコアの高い順に置き、ほかのラベルと重なるものは出さない（枠は出す）。カメラでは、上のバーと凡例・下のボタンの範囲には、枠もラベルも描かない
- カメラの枠の位置: 以前は、canvas を映像の大きさのまま画面に引きのばしていたため、映像（object-fit: cover）と枠がずれていた。canvas を画面の大きさにして、cover と同じ計算で置くように直した（`src/lib/overlay-geom.ts`・テストあり）
- デバッグ表示（枠ごとに、クラス・スコアの数字・追跡の回数）: 開発用の版にだけ入る。本番のビルドには、そのコードが入らない（`vite.config.ts` の `__DEBUG_OVERLAY__`）
  - 開発用の版の作り方: `VITE_DEBUG_OVERLAY=1 npm run build`（または `VITE_DEBUG_OVERLAY=1 npm run dev`）。Vercel では、`debug` ブランチのプレビューが、自動で開発用の版になる（`vite.config.ts` の `DEBUG_OVERLAY`。本番の production では、いつも作らない）
  - 開発用の版の中でも、ふだんはオフ。設定のバージョンの表示を 5 回つづけて押すと、オン・オフ
  - 本番のビルドに入っていないことの確かめ方: `npm run build` のあと `npm run check:no-debug`（`dist/` の中に、デバッグ表示だけで使う文字があれば失敗する）
- 前と後の画像: 作者の手元に残した（このリポジトリには入れていない）。カメラの画面は、写真から作った動画を Chrome の偽カメラに流して撮った

### カメラの画面（一時停止・お休み・カメラの許可）

- 中央の大きなボタン（前は「四つ葉を記録する」。押すと、四つ葉を見つけていなくても発見の画面に移っていた）は、なくした
- 上の「自動で探しています」を押すと、一時停止（「一時停止中」と再開の三角）。もう一度押すと、また探す。押せる範囲は 48px 以上
- 90 秒、動きがない（画面を触っていない・四つ葉の候補を追っていない）と、自動でお休み（「お休み中」）。映像を止めて、電池を減らさない。押すと、また探す
- カメラの許可が、何度もきかれていた原因（コードから分かったこと）
  - Permission 画面で 1 回 getUserMedia を呼び、すぐ止めてから、スキャン画面でもう 1 回呼んでいた（続けて 2 回きかれる）
  - 画面を離れるとき（pagehide）に、カメラのトラックを止めていた。「戻る」で表示されたときは、ページを読み込み直して、また getUserMedia を呼んでいた
  - iPhone の Safari は、サイトのカメラが「許可」になっていないと、getUserMedia を呼ぶたびにきく
- 直し方
  - Permission 画面では、許可を求めない（スキャン画面で 1 回だけ）。すでに許可されていれば、Permission 画面を飛ばす
  - 画面を離れても、トラックは止めない（検出だけ止める）。「戻る」で表示されたときも、読み込み直さない
  - トラックが止まったとき（'ended'。ほかのアプリが使った など）・許可されていないときは、画面のまん中に案内と「カメラを つかう」を出す。再開の前と検出の前にも、トラックが生きているかを確かめる（'ended' のイベントが来ないまま止まることがあったため）
  - 設定に「カメラの 許可」の案内（Safari の「ぁあ」→「Webサイトの設定」→「カメラ」→「許可」）。スキャン画面の「何度も きかれるときは」から開く
- 確かめたこと（パソコンの Chrome・偽のカメラ）: 一時停止・再開、90 秒でお休み・再開、トラックが止まったときの案内と「カメラを つかう」での再開、許可ずみのときに Permission 画面を飛ばすこと。iPhone で何度きかれるかは、実機で確かめる必要がある

### 使うほど合う、端末内の調整（`src/lib/tuning.ts`・`src/lib/tuning-db.ts`）

- 確認のポップアップで選んだ「図鑑に入れる／入れない」（候補のスコアと、選んだ結果）を、IndexedDB（progress の入れ物の `id: 'tuning'`）に残す。外には送らない。新しいものから 1,000 件まで。きろくを消しても残る
- 「入れる」5 件以上・「入れない」5 件以上・合計 20 件以上たまったら、「入れる」と選ばれやすいスコアの境目を推定して、四つ葉の候補を出すしきい値を少しだけ動かす（三つ葉のしきい値は変えない。葉の本数と経験値は変わらない）
  - 推定: 「入れる」の確からしさ = σ(a·(スコア − b)) を当てはめ、境目 b を使う。b はもとの値（写真 0.4）に、傾き a はなだらかな値に引き寄せる（正則化）
  - 動かす量 = (b − もとの値) × 件数 / (件数 + 40)。上げる向き（候補を減らす向き）は、さらに半分（「入れない」は好みのこともあるため）。±0.1 まで
  - 写真から探すとカメラに、同じ差を使う（写真 0.4 → 0.3〜0.5・カメラ 0.5 → 0.4〜0.6）
- 設定の「あなたに合わせて調整する」: 「調整する（おすすめ・既定）」「調整しない」と、「調整を もとに もどす」（2 回押すと、選んだ記録を消す）。画面には数字やしきい値を出さない
- シミュレーション（人工の選択の履歴。`tests/tuning.test.ts`）: ほぼ全部「入れる」人 → 100 件で 0.30（下限）。0.75 未満を「入れない」人 → 20 件 0.44・40 件 0.47・100 件で 0.50（上限）。スコアと関係なく半々に選ぶ人 → 0.40 のまま。20 件より少ないときは動かさない
- 「入れない」の重みを半分にして当てはめる案は、半々に選ぶ人で、しきい値が下がってしまった（候補が増える）ので、やめた。代わりに、上げる向きの動きを半分にしている
- ブラウザで確かめた: 選んだ記録を 300 件入れると、同じ写真（three-leaves の IMG_1378）の四つ葉の候補が 6 → 8。「調整しない」・「もとに もどす」で、もとの値に戻る

### 「ミスも含めて、育てる」（まちがいをおしえる）

- できるのは、**端末の中のしきい値の調整だけ**（上の「使うほど合う、端末内の調整」）。教えた内容を学習データに戻して、モデルを学習し直す機能は、まだない（まちがいの記録は、設定から書き出せる）

- 設定の「まちがいの記録」に 1 行: 「AI は、まだ、まちがえることがあります。おしえてもらった内容は、この端末の中だけに、記録されます。」
- 確認のポップアップで、初めて「入れない」を選んで、まちがいの記録に足したときだけ、上に短いお礼「おしえてくれて ありがとう。記録しました。」（キャラクター smile つき・約 3 秒で消える）。2 回目からは出さない。ほかのお知らせが出ているときは、消えてから出す
- きろくのバッジ「はじめて まちがいを おしえた」（同じとき）。経験値は付けない（「入れない」を増やすと点が増える、ということにしないため）。ランキングや連続日数は作らない
- しくみ: ポップアップを閉じたあと、「入れない」が 1 つ以上あれば、きろくに `teach` のできごとを足す（`src/lib/progress.ts`。テストあり）。きろくを消すと、お礼とバッジは、もう一度出る

### レベル・きろく（`src/lib/progress.ts`・`src/lib/progress-db.ts`）

端末の IndexedDB（入れ物 `progress`。DB の版 4）にだけ保存します。確率やパーセントは出しません。

- **経験値**: 写真から探すで、葉（三つ葉＋四つ葉）1 本につき 1 点。四つ葉を図鑑に保存したら 1 つにつき 100 点（カメラでも、写真でも）。日記カードを作ったら 30 点（1 つの記録につき 1 回まで）
  - 1 枚の写真から入る経験値の上限: 葉の分は 200 点まで、四つ葉の分は 3 つ（300 点）まで（三つ葉を四つ葉と間違えやすい写真で、点が増えすぎないように）。カメラの四つ葉は上限なし
  - 同じ写真（写真の中身から作った SHA-256 の先頭 16 文字が同じ）は、2 回目から 0 点で、本数も増えない（四つ葉の分も）
  - 四つ葉の経験値は、図鑑に保存する処理（`src/lib/save-four.ts`）の 1 か所で入れる
  - 開発用の `?detector=dummy` のときは、写真とカメラの分を記録しない
- **レベル**: Lv1→2 は 100 点。そのあと、次のレベルまでの点が 50 ずつ増える（Lv2→3 は 150 点…）
- **ランク**: たね（Lv1〜2）・めばえ（3〜5）・わかば（6〜9）・みつば（10〜14）・よつば（15〜24）・よつばマスター（25〜）
- **画面**: ホームのレベルのカード → きろくの画面（`kiroku.html`）。写真から探すの結果に「けいけんち ＋◯」。レベルが上がったら、短い紙吹雪つきで知らせる（「視差効果を減らす」がオンなら紙吹雪は出さない）
- 「四つ葉は、約5,000本に1本といわれています」は、よく知られた目安（きろくの画面に 1 行だけ）

### iPhone の操作（拡大・押せる大きさ）

**画面が、すぐ拡大してしまう問題**（2026-10-26）
- 原因: どの画面にも `touch-action` が無かった。iPhone の Safari は、続けて 2 回たたくと、画面を拡大する。確認ポップアップの「入れない」「つぎへ」、手書きの「もどす」、シールなど、速く続けて押すボタンで起きやすい。調べた 15 画面の、押せるもの（のべ 146 個）すべてが、この状態だった（`touch-action` が、自分にも、親にも無い）
- 直し方（`src/styles/global.css` の「リセット・ベース」）:
  - html・body と、触るもの（a・button・label・img・canvas・input など）に `touch-action: manipulation`。ダブルタップの拡大だけが止まり、ピンチの拡大とスクロールは残る（viewport に `user-scalable=no` は付けない）
  - 枠を動かす画面（`.stage`）と、手書きの間のカード（`.diary-preview--ink`）、書く層（`.ink-canvas`）は `touch-action: none`。描く・動かす間に、拡大・スクロールしない
  - ボタン・リンク・ナビに `user-select: none` と `-webkit-touch-callout: none`。画像・canvas にも `-webkit-touch-callout: none`。日記カードのプレビューの画像だけは、長押しで「写真に保存」できるように残す（手書きの間は止める）
  - 入力欄・テキストエリア・select の文字は 16px 以上（`max(16px, 1em)`。ひとことの入力欄は 18px）。16px より小さいと、入力のときに拡大する
- 再現: headless Chrome（iPhone 15 の大きさ・タッチ）でも、Playwright の WebKit（26.0・Windows）でも、ダブルタップで倍率は 1 のままで、再現しなかった。WebKit では、12px の入力欄をタップしても拡大しない。つまり、iPhone の Safari の拡大の動きそのものが、まねされていない。実機での確認が要る

**押せる大きさ**: 15 画面の押せるものを、すべて測った（一覧と、直す前・後の画像は `Pictures\yotsuba-screens\tap-size\`）。すべて 56×56px 以上、隣どうしの間は 12px 以上で、目安（48×48px・8px）を満たしていたので、大きさは変えていない。確認ポップアップの「図鑑に入れる」↔「入れない」は 12px、「ぜんぶ入れない」↔「図鑑に入れる」は 423px、「ぜんぶ入れない」↔「×」は 56px 離れている。

**文字**: 補足の文字（ナビの名前・日付・説明）の 15px を、すべて 16px にした（本文は 17px のまま）。

### 今日のよつば（`gacha.html`・`src/pages/gacha.ts`）

- 1 日に 1 回、四つ葉の形を「ひく」。形は、**この端末の中で、小さなモデル（DiT）が作る**（`src/lib/gacha-maker.ts`・`src/lib/gacha.worker.ts`）。通信するのは、モデルがまだ端末に無いときに、自分のサイトからモデルを取るときだけ
- **形は、日付と端末ごとの値から決まる**（`src/lib/gacha-seed.ts`）。端末ごとの値は、初めてひいたときに、その端末の中で乱数（`crypto.getRandomValues`）で作り、IndexedDB に残す（`src/lib/gacha-device.ts`）。同じ端末の同じ日は同じ形、別の端末では、同じ日でも別の形。**端末どうしは通信しない**（外のサーバーやデータベースは使わない。端末の特徴（フィンガープリント）も使わない）
  - 「すべてのデータを消す」で、端末の値も消える（次にひくと、新しい値になり、その日の形も変わる）
  - 書き出し・読み込み（下の「データを守る」）には、端末の値と今日の形を入れない（別の端末で読み込んだときは、新しい値になる）
- 画面: ひく前 → つくっている間（途中の 4 つの形を、約 2 秒で順に見せる）→ 結果（切り絵・押し花・ドット絵を切り替えられる）→ 図鑑に入れる（確認のポップアップ）。デザインのキャンバス「今日のよつば イメージ」に合わせた
  - 切り絵・押し花は、64×64 の形の輪郭をなめらかにして描く（少しぼかして等高線を取り、角を丸める。`src/lib/gacha-outline.ts`）。ドット絵は、64×64 をそのまま使う
  - 葉脈と、葉ごとの色分けは、「妥当な形」のチェックと同じ葉の分け方（谷の深さ）で付ける（`src/lib/gacha-shape.ts` の `lobeDetails`）
- 説明の 1 行: DiT の形のときだけ「この端末の中で、小さなモデル（DiT）が作った形です」。60 枚から出したときは、説明の 1 行を出さない（図鑑の詳細には「あらかじめ作った形」と出るので、どちらから出たかは分かる）
- 日記カードの文は「今日のよつばが できた！」（見つけた四つ葉ではないので、「見つけた」とは書かない）
- 図鑑の詳細には、出どころを、かならず出す（「端末の中のモデルが作った形」か「あらかじめ作った形」）。DiT の形のときは「数式で作った形で学習したモデルです」も小さく書く
- 設定の画面に「今日のよつばのモデル：準備できています／まだ準備中です」（キャッシュにあるかを調べる。数字は出さない）
- 「図鑑に入れる」は、確認のポップアップのあとで、1 日 1 回まで（60 枚の形を入れた日に、あとで DiT の形が出たときは、DiT の形も 1 回入れられる）。絵は、そのとき選んでいた見た目で保存する。経験値は入れない。見つけた四つ葉ではないので、ホームの「見つけた四つ葉」の数・大きな画像・最近の発見には入れない。まちがいの報告のメニューは出さない。日記カードは、図鑑の詳細から作れる
- 今日の形（64×64。512 バイト）は、**DiT の形だけ** IndexedDB に残す（`src/lib/gacha-today.ts`）。同じ日に開き直したら、モデルを読み込まずに、同じ形を出す。60 枚から出した形は残さないので、次に開いたときは「ひく前」から（DiT が使えるようになれば、その日のうちに DiT の形になる）。「すべてのデータを消す」で消える

### データを守る（設定の「書き出しと 読み込み」。`src/lib/backup.ts`・`src/lib/backup-db.ts`）

- データは、この端末のブラウザの中（IndexedDB）にだけある。ブラウザが空き容量を作るときに消されないように、チュートリアルのあとと、図鑑に初めて入れたときに `navigator.storage.persist()` を頼む（`src/lib/persist.ts`）。断られた・使えないときは、設定に書き出しの案内を出す
- 書き出し: 1 つの JSON（`yotsuba-backup-<日付>.json`）。図鑑（ひとこと・日記の手書き）・まちがいの記録・きろく（経験値・バッジ）・調整・設定。`schemaVersion` 付き。今日のよつばの端末ごとの値と今日の形は入れない
  - 写真を入れるかを選べる。目安 50MB を超えるときは、大きさを出して「写真なしで 書き出す」も選べる
  - 共有の画面（Web Share API）で渡す。使えなければダウンロード。外部との通信はしない
- 読み込み: 形・版・大きさを確かめる。こわれたファイル・新しすぎる版は、はっきりしたエラーにして、何も書きかえない。「足す」（同じ記録は足さない。きろくと設定は今のまま）か「上書き」（先に今のデータの書き出しを案内する）を選び、確認してから書く。1 つのトランザクションで書き、途中で失敗したら元に戻る
- 「すべてのデータを消す」の前に、書き出しを案内する（飛ばせる）。設定に「最後に 書き出した日」を出す（催促はしない）

4. 確かめて通った四つ葉だけを「四つ葉が見つかりました！」として出し、図鑑に自動で保存する。候補だけのときは「四つ葉の候補が、ありました。拡大して、よく見て、確かめてください」と出し、保存しない（候補をタップして確かめ、通ったら、そのときに自動で保存する。「保存」ボタンは作らない）

| 設定 | 代わりの写真: 四つ葉として出す | 正解の四つ葉が残る（今のアプリで見つかる 131 個に対して） | 三つ葉だけ 100 枚: 四つ葉の誤検出 |
|---|---|---|---|
| 前（全体＋タイル 60%・確かめない） | 31 | 131（100%） | 520 |
| 四つ葉と三つ葉のスコアの差（margin 0.3） | 29 | 131（100%） | 514 |
| 全体＋タイル 80% | 26 | 129（98.5%） | 412 |
| いつも確かめる（タイル 80%・3 回中 2 回） | 21 | 114（87.0%） | 242 |
| **採用: いつも確かめる＋候補が 5 個を超える写真は 3 回とも（タイル 80%）** | **13** | **110（84.0%）** | **183** |

- 間違いは、モデルが「自信を持って」間違えている（四つ葉のスコアが高く、三つ葉のスコアはほぼ 0）。そのため、スコアの差（margin）では、ほとんど減らない
- 「確かめる」も同じモデルを使うので、このような写真の間違いの多くは、確かめても通ってしまう（代わりの写真で 26 個のうち 21 個が、3 回中 2 回で通る）
- **目安（本物の四つ葉の 85% 以上が残り、代わりの写真の誤検出が半分以下）には、少し届いていない**（84.0%）。それでも、この設定を採用している

**v2 のときの限界**（v3 で学習し直した理由）

- **三つ葉だけの写真 100 枚では、確かめて通っても、四つ葉の誤検出が 183 個残る**（前は 520 個）
- 「確かめる」も、同じモデルを使う。そのため、モデルが自信を持って四つ葉と間違える種類の葉（三つ葉が一面に生えた写真・カタバミなど）には、確かめても見分けられないという限界がある
- **これ以上減らすには、モデルの再学習が必要な状態である**（三つ葉が一面に生えた写真・カタバミ・シロツメクサの群生の写真を、「四つ葉なし」として学習に入れる）

### 確かめる（確認ステップ）

**v3 からはオフ**（`VERIFY_STEP = false`。理由は「写真から探す」の節）。以下は、v2 で使っていたときの説明です。

写真から探すの結果と図鑑の詳細で、四つ葉の枠をタップすると、その場所を大きくした写真が出ます（いつも出す）。そこで「確かめる」を押すと、同じ葉を、切り抜きの中での大きさを 3 通り（枠が切り抜きの幅のおよそ 20%・35%・50%）に変えて判定し直し、「四つ葉のようです」か「よく見て、確かめてください」を出します。確率やパーセントは出しません。

- モデルには「大きく写った葉ほど、四つ葉と答えやすい」癖があるので、枠の中を拡大して 1 回だけ判定する方法は使っていません
- **決まり: 3 回中 2 回以上、その場所で四つ葉が出たら「四つ葉のようです」**（`src/lib/verify-crops.ts`）。この決まりは、測定の結果を見てから選びました
  - 測定: yotsuba-v2 の学習に使っていない写真 167 枚・正解の四つ葉 199 個（core の valid・Four-LeafCloverFinder・clover-detection2・three-leaves）
  - 目安: 本物の四つ葉の 85% 以上が残り、誤検出の 30% 以上が落ちること

  | 決まり | 本物の四つ葉が「四つ葉のようです」に残る | 誤検出が「よく見て、確かめてください」に落ちる |
  |---|---|---|
  | 3 回とも | 77.7%（101/130） | 78.4%（87/111） |
  | **3 回中 2 回以上（採用）** | **87.7%（114/130）** | **54.1%（60/111）** |

  - 葉が小さく写った写真（clover-detection2）では、本物が残りにくい（2 回以上でも 41.2%）
  - **自分で撮った写真で、測り直す予定**です。結果によって、決まりや `VERIFY_STEP`（`src/lib/detector-config.ts`）を見直します
- 待ち時間を短くするため、途中で答えが決まったら、残りの判定はしません（2 回で決まることが多く、平均 2.0〜2.2 回。答えは 3 回やったときと同じ）。また、枠をタップしてシートが開いた時点で、モデルの読み込みと、最初の 1 回の準備を始めます

### カメラの検出は WASM（2026-10-29 から。作者の決定）

- カメラの検出は、どの端末でも WASM で動かす。WebGPU は使わない（診断用の `?backend=webgpu` を付けたときだけ）。写真から探すは、WebGPU のまま
- 理由（iPhone の Safari 本体・本番での診断の結果。作者が測った）
  - 映像だけ（推論なし）: 60 秒、止まらなかった
  - WASM: 75 秒、止まらなかった（推論 31 回・1 回 391ms）
  - WebGPU・間 300ms: 約 10 秒で強制終了（推論 約 25 回）
  - WebGPU・間 1000ms: 約 10 秒で強制終了（推論 約 9 回）
  - 推論の回数ではなく、時間で止まる。WebGPU のときだけ起きる
- ほかの端末（パソコン・Android）も、WASM にした。パソコンの Chrome では WebGPU で落ちたことはないが、確かめた端末が少ないので、カメラは同じ動きにそろえた
- 推論と推論のあいだ（`src/lib/scan-pace.ts`）: 前の推論が終わってから、直前の推論の時間の半分（最小 200ms）休んで、次を始める。推論は 1 つずつ（前の推論が終わるまで、次のコマを作らない）
  - 推論が、いちばん速かったときの 2 倍以上かかったら（熱くなった など）、直前の推論の時間と同じだけ休む。3 倍以上なら 2 倍休む（長くても 5 秒）
  - 画面が見えないあいだは止める。90 秒、動きがないと、自動でお休み（前のまま）
- WASM の複数のスレッド: 入れない（作者の決定。1 スレッドのまま。COOP/COEP のヘッダーも付けない）。iPhone で測った 1 回の推論: 1 スレッド 1151ms・2 スレッド 621ms・4 スレッド 784ms。測定のページは、このリポジトリには入れていない
- iPhone で確かめた（2026-10-29）: カメラ（WASM）は 211 秒・推論 180 回で止まらなかった。写真から探す（WebGPU）は、同じ写真で 10 回続けても落ちなかった

## 限界

数字は、すべて測った結果です（`training/eval_hardneg.py`・`training/eval_threshold.py`。写真から探すと同じ処理）。

- 今のモデル（v5mix = v3 と v4 の重みを混ぜたもの・しきい値 0.4・確かめない）

  - 大きくて、はっきりした三つ葉の葉を、四つ葉とまちがえることがある（hardcases（作者の手元の写真） の 5 枚では、v3 の誤検出 5 個は、どれも大きな三つ葉の葉の上だった）
  - 三つ葉が密集した場面（上の IMG_1403 など）
  - 見落とした四つ葉の分析（出どころ・大きさ・ぼけ・解像度ごとの割合と、見落としの理由）は、`training/analyze_missed.py` で作れる（評価の写真が要る）
- 評価に使った写真と、使わなかった写真
  - 学習: Roboflow の公開データセット（findclover・rectangle_annotation・Hunting for four-leaf clovers・Clover detection2。CREDITS.md）の train と、iNaturalist の CC0 の写真（カタバミ属・シロツメクサ）
  - 評価（学習には使っていない）: 上のデータセットの valid などの 157 枚（正解の四つ葉 199 個）、three-leaves の 100 枚、iNaturalist の評価専用の 60 枚（`CREDITS-inaturalist.csv` の detector-eval）、hardcases（作者の手元の写真） の 5 枚（ネットの写真。評価専用で、学習にも動画にも使わない）

## Summary (English)

YOTSUBA FINDER is a PWA that finds four-leaf clovers with the phone camera or from photos.
Detection runs entirely on the device (a custom YOLO model, ONNX + onnxruntime-web in a Web Worker); no photo leaves the device and there are no external API calls.
Candidates are shown in a confirmation pop-up, and only the ones the user keeps are saved to the collection.
Measured on photos not used for training, the current model (v5mix, a 75/25 weight average of v3 and v4) detects 126 of 199 labelled four-leaf clovers (63.3%), so it misses about one in three; on 100 clover-only photos it shows 30 false four-leaf candidates (v3: 63).
The "learn from mistakes" feature only adjusts a detection threshold on the device; mistakes are not sent back into training data, and there is no retraining feature yet.
"Today's clover" (gacha.html) draws one clover shape a day with a small on-device diffusion transformer (DiT, flow matching) trained only on shapes generated from formulas; real clover photos were used only to measure the range of those formulas, not for training. The shape is decided by the date and a random per-device value, and devices never talk to each other. If the model cannot run, one of 60 pre-made formula shapes is shown and labelled as such.
The camera uses WASM because, in our iPhone diagnosis, Safari crashed after about 10 seconds when the camera used WebGPU; photo search uses WebGPU with a WASM fallback.
Data stays in the browser on the device. Settings can export everything (collection, diary, progress, mistakes, settings) to one JSON file and import it again (add or replace, validated, written in one transaction).
The confidence hint uses three symbols only (no numbers), with thresholds chosen from measured precision with lower bounds.
It works offline after the first visit, and an end-to-end test checks that no request leaves the app's own origin.
